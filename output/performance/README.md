# اختبار الحملة المعزول — 26 أكتوبر 2026

لم يُستخدم سيرفر Render أو قاعدة Neon أثناء اختبار الضغط. لم يُنشر كود أو يُغيّر إعداد إنتاج. أُنشئت قاعدة محلية جديدة ببيانات وهمية بالكامل، ولم تُنسخ بيانات اللاعبين.

## البيئة وحدود النتيجة

- الجهاز: Apple M4، عشرة أنوية، ذاكرة 24 GB؛ Node v24.11.0.
- سيرفر NestJS في عملية مستقلة، مربوط على `127.0.0.1` ومنفذ مؤقت، وذاكرة V8 القصوى 1 GB. لا يوجد تقييد CPU يحاكي Render.
- PostgreSQL 17 محلي على المنفذ 55441، وثلاثة اتصالات لكل PrismaClient. التطبيق ينشئ أكثر من PrismaClient وفق وحداته الحالية.
- تُحذف مفاتيح الخدمات من بيئة العمليات، ويُحظر اكتشاف وقراءة `.env` قبل تحميل Prisma. يرفض الاختبار أي قاعدة خارج IPv4 loopback أو اسم لا ينتهي بـ`_test` أو كلمة مرور قاعدة.
- جميع استدعاءات fetch الخارجية في عملية السيرفر مرفوضة، وتُعطل وظائف الموسم والتذكير. لا OTP ولا Push حقيقيين.
- السيناريو يستخدم 500 حساب و125 غرفة و3,000 مباراة تاريخية و12,000 مشاركة و25,000 حدث و11,000 محفظة لعبة وهمية.
- النتيجة اختبار محلي قصير؛ لا تثبت تحمّل خطة Render بمعالج واحد و2 GB، أو تأخير الشبكة وحدود Neon، أو زمن واجهة الجوال أو تسليم SMS/Push. تختلف أيضًا نسخة Node المحلية عن Node 20 المحددة في Docker الإنتاج.

## نتائج القراءة

مدة كل مرحلة 60 ثانية؛ لكل لاعب افتراضي دورة غرفة ثم حالة النتيجة كل 3 ثوانٍ. يقرأ الإعدادات والإشعارات كل 30 ثانية، ويجدد جلسته مرة، ويقرأ عُشر اللاعبين الليدربورد كل 15 ثانية. تختلف عناوين IP الوهمية بين اللاعبين والمراحل. يُفحص HTTP و`ok` داخل الاستجابة، لأن بعض أخطاء التطبيق ترجع HTTP 200.

اجتازت بصمات هويات الحسابات وأرصدتها ونتائج الغرف وعضويتها المقارنة قبل وبعد مراحل القراءة. لم تنفذ المراحل اختبار إنشاء الحسابات الجديدة أو إنهاء المباريات؛ اختُبرت الكتابة منفصلة كما يلي.

## مشاكل مؤكدة محليًا

1. **حدود الطلبات على IP مشترك:** ضغط 200 قراءة طبيعية لخمسة لاعبين في نافذة دقيقة أدى إلى 20 استجابة 429. هذا اختبار حجم طلبات الدقيقة مضغوط زمنيًا؛ ليس خمس دقائق لعب على أجهزة فعلية. السبب أن middleware يجمع جميع قراءات `/api/rooms` لنفس IP تحت حد 180 في الدقيقة، بينما كل لاعب يقرأ الغرفة والحالة نحو 40 مرة بالدقيقة.
2. **تكرار اعتماد النتيجة:** في خمس غرف بأربع مشاركات، أدت الموافقات الثلاث المتزامنة بعد موافقة المضيف إلى مباراتين لكل غرفة بدل واحدة. في خمس غرف أخرى مع إعادة طلب موافقة واحدة، سُجلت ثلاث مباريات لكل غرفة. فشلت مقارنة النقاط الفردية في الغرف العشر. لا يوجد ادعاء أن نفس الخلل وقع فعليًا في الإنتاج؛ المشاهدات تخص البيانات الوهمية فقط.
3. مصدر الخلل الثاني: `RoomsService.voteResult` يفحص اكتمال الأصوات ثم يستدعي `finalizeResult` خارج حماية مشتركة. يستقبل كل طلب نسخة قديمة من حالة الغرفة. ينشئ `MatchesService.createMatch` المباراة قبل معاملة تسوية الأرصدة، ولا يوجد قيد فريد يمنع تكرار المباراة للغرفة. يلزم تصميم اعتماد واحد ذري وقابل لإعادة المحاولة قبل النشر، مع معالجة إخفاق التسوية داخل نفس حدود المعاملة.

## اختبار التسجيل

نجحت 100 محاولة تسجيل متزامنة في إنشاء 100 حساب وهمي، وكان زمن p95 نحو 1,713 ms محليًا. يستخدم الاختبار قائمة بريد وهمية مصرحًا لها بتجاوز OTP عبر مسار حسابات المراجعة الموجود أصلًا. يشمل التشفير والتحقق من التفرد وإنشاء الحساب والمحافظ؛ لا يشمل تسليم الرسائل ولا حدود مزوّد OTP أو التحقق الفعلي من رمز مرسل.

## الملفات وإعادة التشغيل

- `test/campaign-load.local.cjs`: البيانات الوهمية والسيرفر المحلي وقياسات 100/250/500 والـIP المشترك.
- `test/campaign-writes.local.cjs`: موافقات النتائج المتزامنة وإعادة الطلب ودفعة تسجيل 100 حساب. يرجع exit code 2 عند فشل سلامة البيانات.
- `campaign-baseline-20261026.json`: نتائج القراءة وحدود الاختبار ومواصفات الجهاز والبصمات.
- `campaign-write-integrity-20261026.json`: نتائج الغرف العشر ودفعة التسجيل.

أنشئ قاعدة PostgreSQL **محلية جديدة**، تنتهي تسميتها بـ`_test`، وطبّق عليها المخطط الحالي. لا تعِد الاختبار على نفس البيانات؛ إنشاء البيانات يرفض قاعدة تحتوي مستخدمين، واختبار الكتابة يرفض غرفًا سبق تسجيل نتائجها.

```sh
# مثال اتصال محلي فقط؛ لا تستخدم .env الخاص بالمشروع.
export DATABASE_URL='postgresql://enzilyqa@127.0.0.1:55441/enzily_campaign_20261026_test?connection_limit=3&pool_timeout=10'
npx prisma db push --skip-generate
npm run build
RUN_LOCAL_CAMPAIGN_LOAD=1 node test/campaign-load.local.cjs
RUN_LOCAL_CAMPAIGN_LOAD=1 node test/campaign-writes.local.cjs
```

قبل حملة كبيرة: إصلاح اعتماد النتيجة وحدود الطلبات، وإعادة هذه الاختبارات، ثم اختبار بيئة staging مماثلة لموارد الإنتاج. لا تُرفع خطط الاستضافة اعتمادًا على نتائج الجهاز المحلي وحدها.
